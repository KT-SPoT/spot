# 의미 Critic MVP 구현 준비안

작성일: 2026-10-02. PR #19의 규칙 Critic 다음 구현을 위한 제안이다.
실행 기능이나 공통 계약을 변경한 문서가 아니며, Notion의 확정 결정으로 취급하지 않는다.

## 이번 단계의 목적

출처 ID·날짜·형식 검사를 통과한 주장도 지역, 진행 단계, 통계의 모집단을
잘못 해석할 수 있다. 의미 Critic은 확보한 자료가 주장을 뒷받침하는지 평가한다.
외부 사실을 모두 확인했다는 승인이나 완성된 행사 기획을 반환하지 않는다.

현재 Graph는 실제 규칙 검사와 일시 오류 최대 1회 재조사를 수행한다.
의미 검토는 미실행 상태다. 이 준비 작업에서 LLM 또는 Scout API를 호출하지 않는다.

## 판단 기준

| 기준 | 확인할 문제 | 판정의 근거 |
| --- | --- | --- |
| 주장과 자료의 일치 | 원문보다 강한 주장을 했는가 | 주장과 수집한 본문 발췌 |
| 지역 범위 | 명지 국제신도시와 에코델타시티를 혼동했는가 | 요청 주소·좌표와 자료의 지역·사업 범위 |
| 진행 단계 | 계획·선정·착공을 운영·완료로 표현했는가 | 자료의 시점과 단계 표현 |
| 모집단·시점 | 유동·주거·직장 인구를 섞거나 기간을 추정했는가 | 검증된 지표, 모집단, 각 지표의 실제 기간 |
| 고객 해석 | 성별·연령 구성만으로 구매 의향을 단정했는가 | 통계 사실과 기획 가설을 구분 |
| 독립 사례 | 같은 행사 보도를 서로 다른 사례로 셌는가 | 사례 그룹과 행사·브랜드·날짜 근거 |
| 지역 차별성 | 비교 자료 없이 다른 상권보다 우수하다고 했는가 | 실제 비교 자료 또는 비교 미확보 표시 |
| 캠페인 관련성 | 제품 체험과의 연결이 사실인가 가설인가 | 근거 → 해석 → 추가 확인 항목의 연결 |

인접 지역 자료는 삭제부터 하지 않는다. 요청 지역의 직접 근거인지, 인접 지역의
참고 맥락인지 구분한다. 자료가 부족한 경우에는 오류 단정 대신 `insufficient`로 둔다.

## 입력과 출력 초안 — 내부 평가용

입력은 요청, 규칙 검사 결과, 제외하지 않은 주장과 출처, 검증된 Quant 지표,
Trend 사례 그룹으로 구성한다. HTML 원본·환경 변수·인증 URL·요청 헤더는 보내지 않는다.
발췌에는 source_id, 확보 방식(`body_excerpt` / `search_snippet`), 수집 시각,
자른 여부를 붙인다. 검색 요약만 있으면 원문 검증 완료로 취급하지 않는다.
현재 Scout 자료에서 이 정보가 없으면 null로 남기고 추정하지 않는다.

모델의 주장별 응답은 아래 내부 필드를 제안한다. 공통 ScoutResult 필드를 추가하지 않는다.

```json
{
  "claim_id": "local:L-001",
  "verdict": "supported",
  "source_ids": ["S-L-001"],
  "reason": "확보한 본문 발췌가 해당 지역의 계획 단계를 뒷받침한다.",
  "suggested_action": "keep"
}
```

- verdict: `supported`, `contradicted`, `insufficient`.
- suggested_action: `keep`, `qualify`, `manual_check`.
- source_ids와 claim_id는 입력 목록에 실제로 있어야 한다. 새 출처·통계·날짜 생성은 거부한다.
- reason은 제공된 자료에 근거해야 한다. 모델의 자체 지식을 출처로 사용하지 않는다.
- `supported`는 제공 자료와 일치한다는 뜻이며 실제 사건의 진위 보장은 아니다.

## 연결 순서

1. `src/critic/semantic.py`에 내부 입력 구성·응답 검증·호출 인터페이스를 구현한다.
2. 아래 합성 예제로 평가기를 검증한다. 실제 모델 평가와 합성 stub 검증을 구분해 기록한다.
3. 규칙 Critic 이후 의미 평가를 선택적으로 실행한다. 기본값은 꺼짐이다.
4. 초기에는 평가를 기록하는 shadow 모드만 사용한다. 모델 응답이 Brief를 자동 삭제하거나
   Scout 재호출을 일으키지 않도록 한다. Critic 최종 상태는 `manual_review`를 유지한다.
5. 사람이 저장된 실제 자료와 판정을 대조한다. 합성 평가만으로 실제 지역 품질을 승인하지 않는다.
6. 검증된 판정을 Brief의 확인 항목에 반영하는 후속 변경을 만든다. 공통 출력 변경이
   필요하면 Issue 제안 → Integrator 검토 → Notion 및 계약 문서 동기화를 먼저 진행한다.

모델과 제공자는 아직 선택하지 않았다. `.env.example`의 `LLM_API_KEY`는 예약된
자리이며 현재 의미 평가에 사용되지 않는다. 선택한 제공자의 인증 방식과 호출 제한을
확인한 뒤 별도 설정으로 연결한다. API 키 값은 로그·평가 파일·Git에 저장하지 않는다.

## 호출 및 실패 정책 초안

- 작업당 의미 평가 호출은 최대 1회. 전체 전송 크기와 응답 크기 상한을 구현 설정으로 둔다.
- 자료가 상한을 넘으면 제외 범위를 표시하고 평가 완전성을 주장하지 않는다.
- 타임아웃·키 미설정·한도·잘못된 JSON·존재하지 않는 출처 ID는 평가 미완료로 처리한다.
- 실패해도 확보한 Brief와 규칙 결과를 반환한다. 자동 pass 또는 의미 평가 자동 재호출은 없다.
- 원문은 분석 대상 데이터로 취급한다. 원문 속 지시문을 실행하거나 외부 URL을 따라가지 않는다.
- 새 원문 수집과 검색어 재설계는 별도 후속 범위다. 모델 평가만으로 자료 부족을 해결하지 않는다.
- 기존 POST 접수 / GET 조회 Webhook과 일시 오류 재조사 상한은 유지한다.

## 준비된 평가와 완료 기준

`samples/critic/semantic_cases.synthetic.json`은 사람이 판정한 9개 합성 예제다.
실제 명지 지역의 사건·인구 수치가 아니다. 현재 실행되는 자동 테스트도 아니다.
각 예제는 claim, evidence, expected를 갖고 있어 구현 후 동일 기준으로 비교할 수 있다.

구현 완료 시에는 응답 형식, 없는 출처 거부, 실패 시 기존 자료 보존, 기본 꺼짐,
작업당 호출 상한을 자동 검사한다. 별도로 실제 모델이 합성 판정 기준을 얼마나
충족하는지 기록한다. 그 다음 저장된 실제 자료를 사람이 대조하고, 서로 다른
2–3개 상권에서 지역 구분과 근거 부족 표시가 유지되는지 평가한다.

이 문서는 구현 순서 준비까지 완료한 상태다. 의미 평가 실행, 원문 추가 수집,
의미 오류 기반 재검색, 자동 품질 승인, n8n 공개 발행은 아직 구현하지 않았다.
