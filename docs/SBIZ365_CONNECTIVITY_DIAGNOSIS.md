## 판단

- 이번 미확보는 기관 전체 장애나 로컬 인증키 오류로 설명되지 않는다.
- 로컬에서는 인증·수집·파싱을 포함한 Quant 전체가 성공했다.
- GCP는 인증 전에 홈페이지 요청도 실패하며, HTTP 라이브러리와 Docker 여부를 바꿔도 동일하다.
- 실패 지점은 GCP에서 기관으로 나가는 접속 경로다. 기관 또는 중간 보안 장비가
  해당 외부 IP/클라우드 대역/해외 경로를 제한하는 가능성이 높지만, 차단 정책은 확인되지 않았다.
- 사용자에게 보였던 이전 로컬 실패와 이번 GCP 실패가 동일 원인이라는 증거는 없다.
  이전 실행 시간·오류 기록이 없으므로 과거 실패는 별도 미확정 상태로 남긴다.

## 다음 조치

기관 운영자에게 서버 공인 IP, 발생 시간, 홈페이지에서도 HTTP 응답 없이 연결이
초기화된다는 현상을 전달해 허용 정책을 확인한다. 키는 전달할 필요가 없다.
IP/대역 제한으로 확인되면 허용 등록 또는 허용되는 국내 실행 환경을 검토한다.
새 리전은 비용·접속 가능성을 확인한 뒤 결정하며 이번 진단에서 서버를 이전하지 않았다.
키 재발급, n8n 변경, 무조건적인 재시도는 현재 증거로는 해결책이 아니다.

## 서울 리전 비교 테스트

2026-10-06 15:35 KST부터 GCP `asia-northeast3-a`에 임시 `e2-micro`를 생성했다.
오리건 운영 서버는 변경하지 않았다. 서비스 계정과 API 권한을 부여하지 않았으며,
10GB 부팅 디스크와 임시 외부 IP만 사용했다. 최대 900초 뒤 VM 자동 삭제를 설정했다.

- 홈페이지와 인증 없는 상세분석 주소: HTTP 200, TLS 검증 성공.
- 오리건 배포 이미지에서 Quant 코드만 복사해 실행했다.
- 기존 SBIZ365/Kakao 인증값은 SSH 파이프로 테스트 프로세스의 메모리에만 전달했다.
  키 값이나 인증 URL은 출력하지 않았으며, VM 메타데이터나 파일에 키를 저장하지 않았다.
- 남부산점 주소, 반경 1,000m로 Quant 전체 실행: `success`, 오류 0개, 지표 26개.
- 인증 진입, 분석 생성, 기본 보고서 및 보고서 2/3/4/6/7/8은 모두 HTTP 200이었다.
- GPT, YouTube, n8n 워크플로, 웹 서비스는 이번 테스트에서 실행하거나 변경하지 않았다.

같은 GCP 제공자의 서울에서는 성공하고 오리건에서는 홈페이지부터 실패했다.
따라서 전체 클라우드 IP 제한보다는 해외 IP/해외 접속 경로 제한이라는 가설에 강한
근거가 생겼다. 기관의 실제 차단 정책 또는 특정 오리건 IP 제한 여부까지 확인한 것은 아니다.
서울 테스트 성공을 운영 서버 이전 완료로 해석하지 않는다.

테스트 후 임시 VM 삭제 완료를 확인했으며, 해당 이름의 VM·디스크 목록이 모두
비어 있음을 확인했다. 고정 외부 IP는 생성하지 않았다. 테스트 사용분의 최종 청구액은
결제 보고서에 반영되기 전이므로 확정하지 않았다.
